# Активация и защита приложения

Документ для владельца приложения: как устроена лицензия, как выдавать коды,
что именно мешает взлому и где проходят честные границы этой защиты.

Коротко: **лицензия бессрочная**. В коде активации нет даты, приложение не
читает системное время при проверке, и «срока действия» не существует ни в
данных, ни в интерфейсе. Перевод часов, откат времени, подмена даты установки —
на лицензию не влияет ничего из этого.

---

## 1. Что видит человек

1. Запуск `AgroPrognoz.exe` → заставка → **экран активации**.
2. Нажимает **«Отправить заявку владельцу»** — открывается его Telegram /
   WhatsApp / почта с готовым текстом заявки (или копирует заявку / сохраняет
   файл `.agrorequest`).
3. Вставляет присланный код из письма (или выбирает файл `.agrolic`) →
   «Активировать».
4. Приложение открывается и больше вопросов не задаёт: активация сохраняется
   на этом компьютере и проверяется при каждом запуске.
5. Внизу боковой панели — «Лицензия: Бессрочная» и серийный номер в подсказке.

На экране активации показан **код этого компьютера** (`XXXX-XXXX`). Он нужен
для персональных кодов и для обращений в поддержку. Персональный код на чужом
компьютере не работает: сообщение «Код выписан для другого компьютера»
объясняет, что делать — прислать владельцу код этого компьютера.

## 2. Код активации

| | |
|---|---|
| Формат | `AGRO-XXXXXXXX-XXXXXXXX-…` — 16 групп по 8 символов, всего 128 символов тела |
| Внутри | 16 байт нагрузки + 64 байта подписи Ed25519 = 80 байт → base32 Crockford |
| Алфавит | `0-9 A-Z` без `I L O U`; `I`/`L` читаются как `1`, `O` — как `0`, регистр и разделители не важны |
| Срок | **нет**. Поля даты в раскладке не существует |
| Уникальность | у каждого кода свой серийный номер (8 случайных байт) — по нему лицензию можно найти в журнале и отозвать |

Нагрузка кода: версия формата, идентификатор продукта, идентификатор ключа,
флаг привязки к компьютеру, серийный номер и (для персональных кодов) отпечаток
компьютера из 4 байт. Всё это подписано закрытым ключом, которого в приложении
нет — поэтому «дорисовать» себе код из установленного приложения нельзя.

Приложение терпимо к вводу: код можно скопировать из письма целиком, с
переносами строк и лишними пробелами — проверка найдёт его в тексте.

## 3. Как выдавать коды (на машине владельца)

Основной инструмент — **«Студия лицензий»**: локальная страница
(`npm run license:studio`) с формой выдачи, журналом и отзывом. Закрытый ключ
создаётся один раз и хранится в `secrets/license-key.json` (каталог в
`.gitignore`, в репозиторий не попадает), студия работает без интернета и ключ
не покидает компьютер владельца. Командная строка осталась для тех же операций:

```bash
npm run license:keygen                          # один раз: создать ключ key-id=1
npm run license:issue -- --count 5              # пять бессрочных кодов
npm run license:issue -- --bind ZZG5-9ZKT       # персональный код (привязка к компьютеру)
npm run license:verify -- "<код>"               # разобрать код: серийник, ключ, привязка
npm run license:keys                            # какие ключи и отзывы зашиты в сборку
npm run license:revoke -- 1a2b3c4d5e6f7a80      # отозвать лицензию по серийнику
npm run license:fingerprint -- ZZG5-9ZKT        # отпечаток компьютера для --bind
```

Журнал выданных кодов пишется в `secrets/ledger.csv`. Формат:
`issuedAt;serial;keyId;kind;shortId;code;name;phone;email;note;status;revokedAt;replaces`
(старый формат license-tool читается и автоматически переводится в новый).
По серийному номеру из приложения клиента всегда можно найти, кому и когда был
выдан код. **Даты живут только в журнале** — это учёт выдачи; на работу
лицензии они не влияют, в коде активации и файле лицензии полей даты нет.

**Персональный код — основной вид выдачи.** Покупатель нажимает на экране
активации «Отправить заявку владельцу» (см. раздел 3.1), владелец вставляет код
компьютера в студию, и полученный код работает только на этом компьютере.
Повторная выдача на тот же код компьютера невозможна молча: студия
предупреждает и предлагает перевыпуск — новый серийник с пометкой «замена» и
автоматический отзыв старого. Универсальный код (без привязки) студия выписывает
только после явного подтверждения и помечает в журнале.

**Отзыв.** Кнопка «Отозвать» в студии или `license:revoke` добавляет серийник в
`electron/license/keys.cjs`. Отзыв действует в следующей сборке: приложение
проверяет сохранённую лицензию заново при каждом запуске, поэтому отозванный
код перестаёт работать после обновления.

**Резервная копия закрытого ключа обязательна.** Без `secrets/license-key.json`
новые коды выписать нельзя; уже выданные продолжат работать (в приложении лежит
открытый ключ). Ключ можно ротировать: `license:keygen --key-id 2` добавит
второй ключ, приложение принимает коды любого ключа из `keys.cjs`.

### 3.1 Канал заявки: покупатель → владелец

Экран активации минимальный: поле для кода и кнопка «Активировать». Код
компьютера, каналы связи и активация файлом свёрнуты в строку «Код компьютера и
заявка» под полем — покупателю, которому код уже прислали, читать нечего, а
тому, кому код нужен, не придётся это искать.

Кнопка «Отправить заявку владельцу» на экране активации собирает текст заявки
(код компьютера, полный идентификатор, версия приложения) и открывает
**собственные** мессенджер или почту покупателя: `tg://`, `https://wa.me/`,
`mailto:` — с уже подставленным текстом. Запасные пути: «Скопировать заявку» и
файл `.agrorequest`.

Что здесь защищается:

- **приложение остаётся офлайн**: никаких запросов наружу оно не делает —
  заявка уходит только через мессенджер/почту самого покупателя;
- **контакт владельца не хардкодится в renderer**: адрес и телефон лежат в
  `electron/license/request.cjs` (main process, в сборке обфусцирован),
  интерфейс получает их по IPC; ссылку на мессенджер строит тоже main process;
- **никаких секретов в сборке**: у канала заявки нет доступа к закрытому ключу,
  журналу и ключам рассылки — их в EXE просто нет (проверяется
  `npm run verify:package`);
- **в браузере заявка не «звонит» домой**: без main process кнопки честно
  говорят, что мессенджер откроется в приложении, а копирование и файл
  работают.

### 3.2 Студия лицензий: границы доверия

Студия (`scripts/license-studio`) — инструмент владельца, в сборку приложения
не попадает (каталог `scripts/` исключён из `app.asar`, что проверяет
`verify:package`). Локальный сервер студии:

- слушает только `127.0.0.1` — снаружи не достучаться;
- требует секретный токен запуска (`x-agro-studio`) — посторонняя страница в
  браузере не сможет управлять выдачей кодов;
- закрытый ключ **не отправляется в браузер никогда**: форма получает только
  результат (код, текст сообщения, журнал).

Необязательный модуль доставки (СМС SMS.ru/SMSC.ru, Telegram-бот, SMTP) тоже
живёт только в студии и включается переменными окружения; без ключей он просто
не включается. Из EXE покупателя отправить что-либо невозможно — этого кода
там нет.

## 4. Слои защиты

### 4.1 Решение живёт в main process, а не в интерфейсе

Renderer не проверяет подпись и не знает открытых ключей. Он спрашивает
состояние и показывает экран активации. Все данные (чтение и запись базы,
сохранение копии, выгрузка CSV) идут через IPC, и **каждый такой канал требует
токен сессии**:

- токен создаётся в main process после успешной активации;
- передаётся в preload и хранится в его замыкании (`contextIsolation` — из
  renderer'а его не прочитать);
- из ответа renderer'у токен вырезается, поэтому он не виден ни в консоли, ни в
  перехваченном IPC;
- каждый запуск — новый токен.

Следствие: правка интерфейса ничего не даёт. Можно нарисовать «активировано»,
но база данных, прогноз и экспорт останутся закрытыми: main process не отдаст ни
байта без активации.

### 4.2 Файлы сборки проверяются по хэшу

`scripts/harden.mjs` считает SHA-256 каждого файла `dist/` и каждого файла main
process и складывает манифест в `electron/license/integrity-data.cjs`. Корневые
хэши манифеста зашиваются **внутрь обфусцированного `guard.cjs`**:

```
guard.cjs (обфусцирован, selfDefending)
   └─ корневые хэши → integrity-data.cjs (манифест)
                          └─ хэши файлов dist/ и electron/
```

Подменить файл — рвётся хэш файла. Подменить манифест — рвётся корневой хэш.
При расхождении приложение не активруется и не отдаёт данные, а показывает
«Файлы приложения изменены». Проверка выполняется при каждом запуске и не
трогает пользовательские данные.

### 4.3 Обфускация main process

В сборку уходит не `electron/`, а `hardened/electron/` — обфусцированная копия
(`javascript-obfuscator`):

- модули лицензии: перемешивание потока управления, мёртвый код, строки в
  base64-массиве с ротацией и сдвигом индексов, разбиение строк, выражения
  вместо чисел, экранирование кириллицы (русских строк «Активация», «лицензия» в
  бинарнике не остаётся), `selfDefending` — код ломается при попытке привести
  его к читаемому виду;
- `main.cjs` / `persistence.cjs`: тот же набор мягче (без `selfDefending` —
  надёжность запуска важнее), но со 100%-ным переносом строк в массив,
  экранированием кириллицы и переименованием имён верхнего уровня
  (`renameGlobals`): ни «АгроПрогноз — Кукуруза», ни `createSplashWindow` в
  бинарнике не остаются;
- `preload.cjs`: щадящий профиль — он работает в sandbox без Node-API.

Обфускация детерминирована (seed от версии и имени файла): одна и та же сборка
даёт байт в байт тот же результат, поэтому хэши воспроизводимы.

### 4.4 Electron Fuses (защита в самом бинарнике)

В `package.json → build.electronFuses`, применяются electron-builder'ом к
`AgroPrognoz.exe`. Это не JavaScript — правкой кода приложения не обходится:

| Fuse | Значение | Что закрывает |
|---|---|---|
| `runAsNode` | **выкл** | `ELECTRON_RUN_AS_NODE=1` → Node REPL с правами процесса |
| `enableNodeOptionsEnvironmentVariable` | **выкл** | `NODE_OPTIONS=--require ./patch.js` |
| `enableNodeCliInspectArguments` | **выкл** | `--inspect`, `--inspect-brk`, SIGUSR1 |
| `onlyLoadAppFromAsar` | **вкл** | подмена кода каталогом `app/` рядом с EXE |
| `enableCookieEncryption` | **вкл** | cookie-хранилище в открытом виде |
| `grantFileProtocolExtraPrivileges` | **выкл** | лишние привилегии `file://` |

Вторым слоем при запуске `electron/license/shield.cjs` проверяет условия:
подключённый инспектор, отладочные переключатели (`--inspect`,
`--remote-debugging-port`, `--js-flags`, `--disable-web-security`), переменные
разработки (`AGRO_DEV*`) и запуск не из упаковки без исходников. В упакованном
приложении инструменты разработчика выключены (`devTools: false`), а повторная
попытка их открыть завершает процесс.

### 4.5 Файл лицензии

Имя — `agroprognoz.license`. Место: у **portable-сборки — рядом с самим EXE**
(см. 4.5.2), у установленной версии и у запуска из исходников —
`%APPDATA%/AgroPrognoz/`. Внутри:

- шифруется `safeStorage` (на Windows — DPAPI: расшифровать может только этот
  пользователь в этой системе), а если он недоступен — AES-256-GCM с ключом из
  HKDF от идентификатора компьютера;
- поверх — HMAC-SHA256 от всего конверта: подмену полей видно без расшифровки;
- идентификатор компьютера дублируется в открытой части: файл, скопированный на
  другую машину, не принимается;
- нечитаемый файл не удаляется, а переименовывается в `*.bad` (материал для
  разбора);
- запись атомарная: временный файл → fsync → rename;
- **дат внутри нет** — хранить «когда активировано» незачем, откатывать нечего.

Сохранённая лицензия при каждом запуске проверяется заново: подпись, продукт,
отзыв, привязка к компьютеру.

### 4.5.0 Куда пишется файл лицензии и почему это безопасно

Правило выбора (`checkmode.cjs`, `licenseDirFor`): если сборка portable
(`PORTABLE_EXECUTABLE_DIR` от electron-builder или `AGRO_PORTABLE_EXE` из нашего
NSIS-скрипта) и этот каталог существует и доступен на запись — файл кладётся туда;
во всех остальных случаях — в каталог профиля. Откат молча не происходит: строка
`license: файл … в …` попадает в лог main process.

Перенос папки с активированным portable-EXE на другой компьютер лицензии не даёт:
конверт шифруется ключом, выведенным из идентификатора машины, и заверен
HMAC-SHA256 по тому же ключу — на чужой машине файл не расшифровывается, а
подмена полей видна до расшифровки. Привязанный код к тому же отвергается по
отпечатку компьютера. То есть «уезжает» только удобство (папку можно копировать
между своими машинами через тот же профиль), но не обход защиты.

### 4.5.1 Проверочный режим копий (`AgroPrognoz-check-<id>.exe`)

У установленной версии лицензия лежит в профиле приложения, и файл один на все
копии программы на компьютере. Отсюда неудобство для владельца: на уже
активированной машине свежескачанный EXE код не спросит, и проверить активацию
«вживую» нельзя. Есть два ответа:

1. **portable-сборка** держит файл лицензии рядом с собой — новая папка = новая
   активация (4.5.2);
2. **проверочный режим** (`license/checkmode.cjs`): копия с именем
   `AgroPrognoz-check-<id>.exe` (или запуск с `--check-instance=<id>`,
   `AGRO_CHECK_INSTANCE=<id>`) использует отдельный файл лицензии
   `agroprognoz-check-<id>.license` — работает и в установленной версии.

Почему это не дыра:

- режим меняет РОВНО одно — имя файла лицензии. Проверка подписи Ed25519,
  привязка к компьютеру, список отозванных серийников, HMAC конверта, проверка
  целостности файлов и Electron Fuses остаются обязательными;
- ничего «разрешить» он не может: вместо сохранённой лицензии будет пустота, то
  есть требование ввести код. Пропуск к данным по-прежнему выдаёт только страж
  после успешной проверки, токена сессии в этом режиме тоже нет;
- данные (база) остаются в общем профиле — копирование не используется как
  способ «починить» лицензию;
- переменные `AGRO_DEV*` и прочие способы запустить приложение «по-домашнему»
  блокируются `shield.cjs` как раньше; `AGRO_CHECK_INSTANCE` в этот список не
  входит именно потому, что он ничего не разрешает.

Тот же режим используют `npm run activation:selftest` и веб-станция
[`station/`](../station) (выдача кода + ссылка на проверочный EXE), чтобы
демонстрация активации была воспроизводимой, а не «на словах».

### 4.6 Вне Electron приложение не работает

Production-сборка, открытая как обычная страница (например, кто-то распаковал
`app.asar` и раздаёт `dist/` статикой), показывает отказ: моста `window.agro`
нет, данных нет, активация невозможна. Ветка «режим разработки» в
production-бандле вырезана статически (`import.meta.env.DEV` → `false`), поэтому
включить её в готовой сборке нельзя. Проверяется в CI тестом `npm run test:gate`.

### 4.7 Мелочи, которые тоже работают

- `asar: true`, `asarUnpack` убран — `dist/` лежит внутри архива, а не рядом;
- из упаковки исключены исходники `calculations/` и `node_modules/`;
- перебор кодов замедляется после нескольких неудач (пауза растёт);
- IPC-каналы доступны только главному окну (`event.sender === mainWindow.webContents`);
- файл лицензии для активации выбирается в системном диалоге — renderer не
  передаёт путь и не видит содержимое;
- разрешение дано только на буфер обмена (вставить код / скопировать
  идентификатор), остальные запросы разрешений отклоняются.

## 5. Честные границы

Офлайн-приложение без сервера активации нельзя сделать невзламываемым: у
человека с исполняемым файлом и достаточным временем всегда есть теоретическая
возможность его пропатчить. Задача этой защиты — сделать взлом дороже покупки
лицензии и непригодным для массового распространения. Что здесь реально:

- код нельзя **подделать** (нужен закрытый ключ Ed25519) и нельзя **подобрать**
  (2⁶⁴ серийников, подпись на 2¹²⁷ работы);
- нельзя обойти активацию правкой интерфейса — данные выдаёт только main process;
- нельзя подменить файлы сборки — проверка целостности и `onlyLoadAppFromAsar`;
- нельзя запустить приложение как Node или подключить к нему отладчик — фьюзы;
- нельзя перенести файл лицензии на другую машину;
- нельзя просто так раздать купленный код знакомым — персональный код
  привязан к одному компьютеру, а повторная выдача видна владельцу в журнале
  студии и отзывается одной кнопкой.

Что остаётся на стороне злоумышленника с навыками реверса: дизассемблирование
обфусцированного main process и ручная правка `guard.cjs` внутри
перепакованного `app.asar`. Это часы работы и пересборка под каждую версию —
именно на это и рассчитан порог.

**Что усилит защиту сильнее всего остального (требует вложений):**

1. **Подпись кода** (сертификат Authenticode, ~$200–400/год). Даёт SmartScreen-
   репутацию и, главное, позволяет включить fuse
   `enableEmbeddedAsarIntegrityValidation`: тогда `app.asar` проверяется самим
   Electron до запуска JavaScript. Сейчас этот fuse намеренно **не включён**:
   на Windows он требует вшить в EXE ресурс `Integrity/ElectronAsar` с хэшем
   заголовка архива (electron-builder этого не делает), а без него приложение
   не запустится вовсе. Включать можно только вместе с вшиванием ресурса и
   проверкой на живой машине.
2. **Сервер активации** (даже один запрос при активации): привязка к машине на
   стороне сервера, мгновенный отзыв, статистика утечек, ограничение числа
   активаций на один код.
3. **Bytecode (bytenode)** для модулей лицензии: V8-байткод вместо JavaScript.
   Требует компиляции той же версией Electron, что и сборка, и проверки на
   Windows — поэтому в этот релиз не включён.

## 6. Как это проверяется

| Проверка | Где |
|---|---|
| 179 unit-тестов: формат кода, подпись, отзыв, привязка, хранилище, целостность, условия запуска, страж, идентификатор компьютера на трёх платформах, поле ввода кода | `npm test` (`tests/license.test.mjs`) |

| «В модулях лицензирования нет обращений к часам» (включая новый `request.cjs`) — статическая проверка бессрочности | `npm test` |
| Обфускация не сломала код: синтаксис каждого файла, ядро, целостность (включая порчу файла и подмену манифеста), полный цикл активации, загрузка обфусцированного preload с подставным `electron` (мост `window.agro` цел, токен сессии не раскрыт, мусор на вводе отклонён) | `npm run harden` (самопроверка, 58 проверок) |

`npm run harden` и `npm run verify:package` можно запускать и локально — они не
требуют Windows (проверяется содержимое сборки, а не запуск EXE).

## 7. Порядок сборки релиза

```bash
npm ci
npm run icon && npm run prepare:assets
npm test
npm run build          # dist/
npm run dist:win       # patch-portable-nsi → harden → electron-builder
npm run verify:package # разбор release/win-unpacked: asar, целостность, фьюзы
```

CI делает то же самое в job `portable` и публикует
`AgroPrognoz-<version>-portable.exe`. Закрытый ключ лицензий в CI не нужен и не
передаётся: сборка проверяется выдуманными кодами, а настоящие выписывает
владелец локально.
